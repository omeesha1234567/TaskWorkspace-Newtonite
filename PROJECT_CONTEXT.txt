1. PROJECT OVERVIEW
================================================================================

1.1 What the Application Does Today
Newtonite Task Tracker is an enterprise-oriented, multi-tenant, collaborative task
and work-item management SaaS web application built with Python and Django.
It is engineered specifically for engineering teams operating under operational pressure,
providing:
- Team-scoped multi-tenancy with distinct organizational workspaces.
- Scoped Role-Based Access Control (RBAC: Admin, Manager, Member) preventing IDOR.
- Optimistic Concurrency Control (OCC) with atomic version checks preventing lost updates.
- Idempotency key architecture preventing duplicate task creations on retried requests.
- Server-enforced task lifecycle state machine (OPEN <-> IN_PROGRESS -> RESOLVED -> OPEN).
- Granular, immutable audit activity logs storing structured JSON snapshots of field diffs.
- Interactive analytics dashboard with Chart.js charts (Status, Priority, Trend, Workload).
- Task attachments management with secure file uploads, download streaming, and disk cleanup.
- Workspace invitation workflows (invite via email, in-app notification, accept/decline/revoke).
- In-app notification center with automated overdue/today deadline detection and unread badges.

1.2 Architectural Style & Framework
- Architectural Style: Modular Django Monolith following Model-View-Template (MVT).
- Decoupling Layer: Dedicated Domain Service Layer (tasks/services.py) and Policy Layer (tasks/permissions.py).
- Backend Framework: Django 6.0.5 / 6.1.2 on Python 3.14.3.
- Database Engine: SQLite 3 (configured at BASE_DIR / 'db.sqlite3') with composite B-tree indexes and WAL mode.
- Frontend: Server-side rendered Django HTML5 templates, Vanilla CSS Design System (static/css/app.css) with light/dark theme tokens, and unobtrusive Vanilla JavaScript (static/js/app.js).
- Charting: Chart.js 4.4.1 loaded via CDN (UMD build).
- Authentication: Django built-in session authentication (django.contrib.auth) using PBKDF2 (and MD5 hasher in test runs).

1.3 Main Entry Points & Execution Flow
- WSGI Entry Point: config/wsgi.py -> config.settings -> config.urls.
- ASGI Entry Point: config/asgi.py (available for asynchronous servers).
- Administrative Tasks: manage.py (standard Django CLI).
- URL Routing: config/urls.py delegates '/admin/' to Django Admin and '' to tasks.urls.
- Context Processing: tasks.context_processors.global_context injects unread notifications and pending invitation counts into all rendered templates.

4.2 End-to-End Request Lifecycles

Lifecycle A: User Onboarding & Registration
1. User submits /register/ with username, name, email, and password.
2. Form clean() checks for username/email uniqueness (case-insensitive).
3. User is created in auth_user.
4. TeamService.create_team() automatically provisions a default workspace ("<Username>'s Team") and creates a TeamMembership with role=ADMIN.
5. User is logged in via django.contrib.auth.login().
6. Redirects to / (dashboard).

Lifecycle B: Idempotent Task Creation
1. User visits /tasks/new/. TaskCreateForm initializes with a unique UUID idempotency key in a hidden field.
2. Assignee select is populated only with members belonging to user's first accessible team.
3. User submits POST. TaskService.create_task() checks IdempotencyRecord inside an atomic transaction.
4. If the key already exists for this user and action, the existing task is returned immediately.
5. If new: Task record is inserted, IdempotencyRecord is stored, ActivityEvent (TASK_CREATED) is saved, and assignee notification is dispatched.
6. User redirected via PRG pattern to /tasks/<new_id>/.

Lifecycle C: Optimistic Concurrency Controlled Task Editing
1. User visits /tasks/<id>/edit/. Form embeds hidden field: <input name="version" value="1">.
2. User submits changes. View passes submitted_version to TaskService.update_task().
3. TaskService runs atomic update:
   Task.objects.filter(pk=task.pk, version=submitted_version).update(..., version=F('version')+1)
4. If rows_updated == 0: Another user updated the task in between. StaleUpdateError is raised.
5. View catches StaleUpdateError, fetches current task state from database, renders edit.html showing a conflict alert and side-by-side comparison, and updates the form version field.
6. If rows_updated == 1: Update succeeds, field diff is logged in ActivityEvent, notifications sent if reassigned or status altered, and redirects to task detail.

Lifecycle D: Fast Workflow State Transition
1. User clicks status transition button on task detail or list.
2. POST to /tasks/<id>/transition/ with new_status and version.
3. TaskService.validate_transition() validates against VALID_TRANSITIONS state machine.
4. Atomic conditional update increments version and transitions status.
5. ActivityEvent (STATUS_CHANGED, TASK_RESOLVED, or TASK_REOPENED) logged.
6. Redirects to task detail with flash success message.

  * MEMBER: Individual contributor (view team tasks/feed, create tasks, edit tasks assigned to or created by them, transition status of assigned tasks).

6.3 Server-Side Authorization Enforcement
- Location: tasks/permissions.py contains pure permission evaluation functions:
  * is_system_admin(user)
  * get_user_team_role(user, team)
  * can_view_team(user, team)
  * can_manage_team(user, team)
  * can_create_task(user, team)
  * can_view_task(user, task)
  * can_edit_task(user, task)
  * can_change_task_status(user, task)
  * can_archive_task(user, task)
  * can_delete_task(user, task)
  * can_change_member_role(actor, target_membership, new_role)
  * can_remove_member(actor, target_membership)

6.4 Anti-IDOR Queryset Scoping
Views NEVER execute unrestricted queries like Task.objects.all().
Instead, they invoke:
- get_accessible_teams_qs(user): Filters Team.objects.filter(memberships__user=user).
- get_accessible_tasks_qs(user, include_archived=False): Filters Task.objects.filter(team__memberships__user=user).
Superusers bypass filters and access all records.

6.5 Known Authorization Subtleties
- Direct object lookups via pk (e.g. in task_detail_view) execute get_object_or_404, followed immediately by an explicit can_view_task() check raising PermissionDenied (HTTP 403) on unauthorized requests.
- Member role edit rights are restricted: a MEMBER cannot edit tasks created by someone else unless assigned to them.

7. WORKFLOWS & BUSINESS RULES SPECIFICATION
================================================================================

7.1 Task Workflow State Machine
States:
- OPEN: Initial active state upon creation.
- IN_PROGRESS: Work actively underway.
- RESOLVED: Task completed and verified.

Permitted Transitions:
- OPEN -> IN_PROGRESS
- OPEN -> RESOLVED
- IN_PROGRESS -> OPEN
- IN_PROGRESS -> RESOLVED
- RESOLVED -> OPEN (Reopened)

Forbidden Transitions:
- * -> RESOLVED on initial task creation (tasks must be created as OPEN or IN_PROGRESS).
- RESOLVED -> IN_PROGRESS (must be reopened to OPEN first).
- Any attempt to execute an invalid transition raises InvalidWorkflowTransitionError (ValidationError).

7.2 Concurrency Safeguards (OCC)
- Field: Task.version (PositiveIntegerField, default=1).
- Execution:
  Task.objects.filter(pk=task.pk, version=submitted_version).update(..., version=F('version')+1)
- If updated_rows == 0, a concurrent transaction updated the record first.
- StaleUpdateError is raised and captured by views.py, triggering HTTP 409 conflict reconciliation.

7.3 Idempotency Safeguards
- Client generates or receives a UUID key upon form initialization.
- Submissions check IdempotencyRecord with unique constraint on (user, key, action).
- If retried, previously created task instance is returned without duplicate insert.

7.4 Referential Integrity & Invariant Safeguards
- Assignee Invariant: Assignee must be an active member of the task's team. Enforced in Task.clean() and TaskService.
- Sole Admin Invariant: A team cannot have its last ADMIN removed or demoted. Enforced in permissions.py.
- Member Removal Invariant: If a member is removed from a team, all their assigned tasks in that team are safely set to assignee=None inside the atomic transaction, preserving task records and audit history.

7.5 Audit Trail Guarantees
- Every state change writes an ActivityEvent within the same transaction.atomic() block.
- ActivityEvent captures actor, team, task, event_type, details, previous_state JSON, and new_state JSON.

- Limitation: Live updates require manual page refresh or user interaction; real-time push (WebSockets via Django Channels) is not configured.
- Mitigation: Post-Redirect-Get pattern and clean response times make polling or manual navigation fast.

18.2 Feature A: Team Shared Document Library
--------------------------------------------------------------------------------
Data Model: tasks/models.py -> SharedDocument
Fields:
- id: BigAutoField (Primary Key)
- team: ForeignKey(Team, on_delete=CASCADE, related_name='shared_documents')
- task: ForeignKey(Task, null=True, blank=True, on_delete=SET_NULL, related_name='shared_documents')
- uploader: ForeignKey(User, on_delete=CASCADE, related_name='uploaded_shared_documents')
- file: FileField(upload_to=shared_document_upload_path, max_length=500)
- display_name: CharField(max_length=255)
- description: TextField(blank=True, default='')
- file_size: PositiveIntegerField()
- content_type: CharField(max_length=100, default='application/octet-stream')
- created_at: DateTimeField(auto_now_add=True, db_index=True)
- updated_at: DateTimeField(auto_now=True)

Storage Architecture & Path Partitioning:
- Logical Folders:
  * Team General: `shared_documents/team_<id>/general/<safe_filename>`
  * Task Specific: `shared_documents/team_<id>/task_<id>/<safe_filename>`
- Filename Sanitization:
  Base filenames are sanitized via slugification while preserving original extensions. A collision-resistant 8-character UUID prefix is inserted (`slug_uuid8.ext`) to prevent race condition overwrites and filesystem collision attacks.
  Display name stores the exact original filename entered by the user.

Upload Validation Rules (tasks/services.py -> SharedDocumentService):
- Maximum file size: 25 MiB (26,214,400 bytes).
- Empty or missing files rejected with ValidationError.
- Dangerous file extensions strictly rejected: .exe, .bat, .cmd, .sh, .php, .py, .pl, .cgi, .js, .vbs, .ps1, .jar, .scr, .pif, .com.
- Permitted document formats: PDF, Microsoft Office (docx, xlsx, pptx, doc, xls, ppt), text files (txt, md, rtf, log), CSV/TSV, and standard image formats (png, jpg, jpeg, gif, svg, webp).
- Task-Team Invariant: If a task is selected, it must belong to the specified team (`task.team_id == team.id`). Cross-team task attachment attempts immediately raise ValidationError.
- Transactional Integrity: Document records are created atomically alongside an immutable ActivityEvent (`DOCUMENT_UPLOADED`). If the database transaction fails, uploaded files are cleaned up to prevent orphaned disk files.

Deletion & Download Semantics:
- Download Endpoint (`GET /documents/<id>/download/`):
  Streams file via FileResponse with `as_attachment=True` and sanitized `filename=doc.display_name`. Access requires authenticated team membership verified on the server. Direct unauthorized media URLs are prevented.
- Deletion Endpoint (`POST /documents/<id>/delete/`):
  Requires CSRF token. Deletes the physical file from the storage backend via `doc.file.delete(save=False)` followed by `doc.delete()`. Records an immutable `DOCUMENT_DELETED` ActivityEvent.

RBAC Policy for Shared Documents:
- Any authenticated member of the team can view the document library, browse folders, and download files.
- Any authenticated member can upload documents to the general library or to any task in their team.
- Team Admins and Team Managers can delete any shared document in their team.
- Team Members can delete only documents uploaded by themselves. Attempting to delete another user's document raises PermissionDenied (HTTP 403).
- Non-members receive HTTP 403 on all document views, uploads, downloads, and deletion endpoints.
- Removing a member immediately revokes access to the document library and download endpoints.

Coexistence with TaskAttachment:
- TaskAttachment: Remains untouched as task-detail-specific attachments with direct inline association.
- SharedDocument: Team-wide document library with optional task filtering and general team file sharing.
- Task detail view (`templates/tasks/detail.html`) provides a direct badge and table linking to associated shared documents, maintaining clear feature separation.

- Development mode uses `django.core.mail.backends.console.EmailBackend`.
- Production mode supports environment-driven SMTP credentials (`EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`).

Atomic Acceptance & Rejection Workflows:
- Acceptance (`POST /invitations/<id>/accept/`):
  1. Verifies authenticated user matches the invitation's recipient email (`user.email.lower() == invitation.email.lower()`).
  2. Ensures invitation is in `PENDING` state and not expired.
  3. Atomically creates `TeamMembership` with the specified role and updates invitation status to `ACCEPTED`.
  4. Records `MEMBER_JOINED` ActivityEvent and creates an InAppNotification for the inviter.
- Decline (`POST /invitations/<id>/decline/`):
  Atomically marks invitation as `DECLINED` without creating team membership.
- Anti-Tampering: Unauthorized users cannot accept, decline, or inspect another user's invitation by manipulating IDs.

18.4 Feature C: Persistent Unread Audit Indicator
--------------------------------------------------------------------------------
Data Model: tasks/models.py -> UserActivityReadState
Fields:
- user: OneToOneField(User, on_delete=CASCADE, related_name='activity_read_state')
- last_read_event_id: PositiveIntegerField(default=0)
- updated_at: DateTimeField(auto_now=True)

Architecture & Performance:
- Immutable Audit Guarantee: `ActivityEvent` records are never mutated or updated. Read tracking is managed strictly via the per-user cursor (`last_read_event_id`).
- Scoped Efficiency: Injected globally via context processor `tasks/context_processors.py -> has_unread_audit`.
  Evaluates: `ActivityEvent.objects.filter(team__in=user_teams, id__gt=last_read_id).exists()`.
  Uses `.exists()` without loading large querysets, avoiding N+1 queries.
- UI Indicator:
  A vibrant red pulsing dot (`.audit-unread-dot`) appears directly on the "Activity" sidebar navigation link.
  Accessible via `aria-label="New unread activity events"` and screen-reader assistance text.
- Read Lifecycle:
  1. When a new audit event occurs in any team the user belongs to, the dot lights up.
  2. Visiting the Activity view (`GET /activity/`) automatically updates the user's `last_read_event_id` to the highest event ID currently accessible, clearing the dot.
  3. If another user or system action creates an activity event subsequently, the dot immediately reappears.
  4. Isolation: Each user has an independent read cursor. One user marking activity read has zero impact on other users.
  5. Updates Centre Independence: Visiting `/updates/` (concurrency monitor) does NOT mark audit activity as read.

20.1 ROOT CAUSE ANALYSIS & STATIC MANIFEST REPAIR
------------------------------------------------
1. WhiteNoise CompressedManifestStaticFilesStorage Missing Manifest Entry:
   - Root Cause: WhiteNoise's CompressedManifestStaticFilesStorage requires a pre-built
     manifest ('staticfiles.json') generated via 'collectstatic'. During automated test runs
     (pytest and django test), tests rendered templates calling `{% static 'img/leaf_emblem.svg' %}`.
     Because STATICFILES_STORAGE pointed to CompressedManifestStaticFilesStorage and no pre-built
     manifest was guaranteed during in-memory or headless test runs, WhiteNoise raised ValueError.
   - Resolution: In `config/settings.py`, detected testing mode (`'test' in sys.argv or 'pytest' in sys.modules or os.environ.get('PYTEST_CURRENT_TEST')`).
     When testing, dynamically set `STORAGES["staticfiles"]["BACKEND"] = "django.contrib.staticfiles.storage.StaticFilesStorage"`
     and `WHITENOISE_AUTOREFRESH = True`.
     In production/live mode, `whitenoise.storage.CompressedManifestStaticFilesStorage` is strictly
     preserved with gzip/brotli compression and immutable content-hashed cache busting.
   - WhiteNoise Warning Elimination: The 25 missing-directory warnings on `staticfiles/` were
     eliminated by enabling `WHITENOISE_AUTOREFRESH = True` during test runs, and adding
     `python manage.py collectstatic --no-input` into `.github/workflows/test.yml`.
   - Brand Emblem References: Fixed hardcoded `/static/img/leaf_emblem.svg` paths in auth templates
     (`login.html`, `register.html`, `password_reset.html`, `password_reset_confirm.html`)
     to standard `{% load static %}` and `{% static 'img/leaf_emblem.svg' %}` tags.

20.2 TASK CREATION & DYNAMIC ASSIGNEE SELECTION REPAIR
------------------------------------------------------
1. Form Dynamic Choice Validation:
   - Defect: `TaskCreateForm.__init__` previously hardcoded assignee choices based strictly on
     `self.user_teams.first()`. When a user selected an alternate team in the UI (e.g. team_beta)
     and chose an eligible member of that team, form submission rejected the choice with a field
     validation error because the member was not in team_alpha's queryset.
   - Fix: Updated `TaskCreateForm.__init__` to inspect `self.data.get('team')` or `self.initial.get('team')`
     and filter `assignee` choices by that specific team's membership.
   - Server-Side Cross-Team Invariant: Added rigorous cross-team validation in `TaskCreateForm.clean()`
     and `TaskEditForm.clean()` to independently verify that `assignee` is an active member of `team`,
     blocking forged form submissions or IDOR bypass attempts.
2. Edit Task Notification & Activity Diff Preservation:
   - Defect: In `task_edit_view`, Django ModelForm's `is_valid()` mutated the in-memory task instance
     before passing it to `TaskService.update_task`. When `update_task` checked `if task.assignee != assignee:`,
     it was comparing the mutated in-memory object against itself, skipping the assignee change audit event
     and notification.
   - Fix: Updated `TaskService.update_task` to fetch pristine `db_task` from database inside the atomic
     transaction to accurately diff original vs updated fields, reliably dispatching `ASSIGNMENT_CHANGED`
     activity logs and `InAppNotification` records.
3. JavaScript Fetch UX Polish:
   - Updated `static/js/app.js` dynamic member fetching on `#task-team-select` with explicit loading,
     empty, and error states, preserving current selections and safely handling network failures.
